The model

A preset is a recipe. A class subscribes to recipes.

The thing that nearly sank this design was asking "what quality is this photo?" — because a photo in two classes has two answers. Turning it around fixes it: quality belongs to the recipe, not the photo. A class doesn't set a quality; it declares which recipes its members need. A photo in two classes needs both, so it gets both.

The union rule has one more benefit worth stating plainly: the phase-2 ladder is not a new feature. Responsive widths are just more presets with a width set. The generator, the manifest shape, the staleness check, the reader lookup and the savings maths are all written once, in phase 1, and phase 2 only adds rows to a config object.

Deliberately deferred

Phase 1 ships the preset registry but only the workspace default subscription — no per-class subscribe UI, no width. That means the multi-class union has nothing to unify yet, which is exactly why phase 1 can't get it wrong. Per-class subscription and widths land together in phase 2, on a data model that already expects them.

Rules the generator obeys

  • Originals are never touched. Not overwritten, not moved, not deleted. Every derivative is additive; deleting media/derived/ entirely is always safe and always recoverable by a backfill.
  • Orientation and colour are preserved explicitly. fixed in r2 sharp neither auto-rotates nor keeps the ICC profile unless told, so every pipeline is sharp(src).rotate().withMetadata() at minimum. This repo already has an orientation discipline (core/images.ts, Item 13) precisely because phone photos depend on the EXIF tag — a derivative that ignores it renders sideways. See the quality section for why the SSIM score cannot catch this.
  • A derivative bigger than its original is discarded. Already-optimised small PNGs and screenshots frequently grow under re-encode. The entry records skipped: "larger" and the current recipe, so it is not retried until the recipe actually changes.
  • Non-images are recorded, not attempted. A PDF or a video gets skipped: "unsupported" — also stamped with the current recipe — so the Compression page can say "389 of 412 covered, 23 can't be" instead of looking incomplete.
  • Every skip carries a recipe. fixed in r2 Staleness is a recipe mismatch, so an entry with no recipe mismatches everything and would be retried on every single backfill forever — exactly what the skip is supposed to prevent.
  • Generation never blocks a request. Upload responds as soon as the blob is registered; the derivative is queued behind it. A slow AVIF encode can't make the upload feel slow.
  • Every ingestion path is hooked, not just upload. fixed in r2 registerBlob has two callers — api/files/upload and api/google-photos/import. Wiring only the first leaves every imported photo uncompressed until someone runs a manual backfill.

Names are clean and shareable, which is a deliberate choice with a known cost — see Keeping caches honest. Because two originals can share a stem (photo.jpg and photo.png both want photo.webp), the collision rule in Risks applies.

Static-assets mode

In static-assets mode the blob dir is the published asset root and the reader synthesises ${baseUrl}/${filename}. Derivatives go inside that root as <assetsDir>/derived/<preset>/, so baseUrl composes with no extra config. A single getDerivedDir(preset) resolver hides the classic-vs-static difference, exactly the way getGlobalFilesDir() already does.

Correction — r1 invented a risk that cannot occur

Revision 1 claimed manifest.reconcile() would scan derived/ and mint phantom file ids for it, and shipped an acceptance criterion to guard against that. Both were wrong. reconcile() scans nothing — it receives diskNames: string[] (manifest.ts:284), and its only producer readGlobalBlobNames() already filters d.isFile() (manifest.ts:332). Independently, adoption defaults to !isStaticAssetsMode() (manifest.ts:288) — so in the exact mode that was flagged, nothing is auto-minted at all, deliberately and documented.

The r1 acceptance criterion "reconcile() ignores the derived directory" tested a no-op and has been deleted. Nothing needs doing here.

Real risk r1 missed — the storage-location move leaves derivatives behind

R1 claimed the Item 46 move "carries them for free". It does not. migrateBlobs iterates a flat list of manifest file_names and copies fromDir/name → toDir/name (assetsMigrate.ts:215-300); it never walks subdirectories, and derivatives are not in that name set. After a classic ↔ static switch the manifest still asserts every derivative exists while the new location is empty, so every variant() URL 404s until a full backfill — silently, since the originals still resolve.

Phase 1 must extend migrateBlobs to walk derived/<preset>/, and include derivative bytes in its free-space preflight (assetsMigrate.ts:238-256).

Manifest entry

Derivatives hang off the existing per-blob entry rather than living in a second file, so one manifest read still answers everything the grid and the reader need.

This is not additive — an un-declared key is destroyed, not preserved

ManifestEntrySchema is a bare z.object (manifest.ts:29), so zod's default strip applies: any key not in the schema is silently dropped on .parse(). Every mutator round-trips readManifest() → parse → mutate → write (manifest.ts:57), so a derived block would survive only until the next setClassMembership / renameFileId / setEntryDimensions / reconcile write, then vanish with no error.

The reader has the same hazard for a different reason: parseManifest hand-whitelists fields (reader/manifest.ts:83-90), so it drops derived too — which would break baseUrl-mode synthesis, since that path reads the manifest rather than a glob.

Phase-1 work, not an implementation detail: extend ManifestEntrySchema, extend ManifestFileEntry + parseManifest on the reader side, and audit every manifest writer. fixed in r2

Staleness is a comparison, not a timestamp race. A derivative is stale when its stored recipe differs from the preset's current recipe string, or its source_size differs from the original's current size.

…but entry.size is not the reliable field r1 assumed

R1 called both halves "cheap fields already in memory, so staleness costs nothing". The recipe half is true. The size half is not:

  • size is written only at mint (manifest.ts:97), and mintFileId returns early on an existing name without updating it (manifest.ts:93) — so an overwrite re-upload leaves the stale size, and the re-upload detector never fires.
  • reconcile()'s adoption path creates entries with no size at all (manifest.ts:300), and nothing ever backfills it — backfillDimensions does width/height only (classRepo.ts:884). Every hand-dropped blob has size: undefined permanently. This is already visible today: file:size renders empty for those rows.

Consequence: the headline savings total cannot be computed for any reconcile-adopted blob. Phase 1 must add a size backfill/refresh to reconcile — which also fixes an existing display bug — and until it lands, the staleness check is an fs stat, not a free in-memory compare. fixed in r2

What "noticeable" means

You wanted a number, not a slider you have to stare through. The number is SSIM — structural similarity between the original and its derivative, computed at generation time and stored on the manifest entry. It correlates with human judgement far better than PSNR and, crucially, it needs no new dependency: it's about sixty lines of arithmetic over two raw greyscale buffers that sharp already produces.

How it's computed

  1. Decode both images to raw greyscale at a matched size — longest edge 512 px — via sharp(…).greyscale().raw(). Verified working on the installed sharp 0.34.2 / libvips 8.16.1: returns a 1-channel uchar buffer.
  2. Slide an 8×8 uniform window computing per-window means, variances and covariance; average the windows.
  3. Store the result to three decimals. Cost is tens of milliseconds, against an encode measured in hundreds — comfortably worth it, but r1's "a few milliseconds" was padding. fixed in r2

Two simplifications worth naming rather than implying textbook SSIM: this uses a uniform 8×8 window where the reference implementation uses an 11×11 Gaussian, and it compares luma only — which means it systematically over-scores exactly the chroma-subsampling artifacts WebP introduces at q80. Both are acceptable for ranking files against each other, which is all the flagged list needs; neither would be acceptable for publishing an absolute quality claim.

Honest caveat, stated in the UI

For a resized preset the two images aren't the same size, so the original is downscaled to the derivative's dimensions before comparison. The score therefore measures codec loss, not the resize — a 400 px thumbnail scoring 0.96 is not "4% worse than the original photo", it's "a good 400 px rendering". The Compression page labels resized presets' scores accordingly rather than letting them be compared against full-size ones.

What this metric is blind to — and it's the likeliest real defect

SSIM compares the two buffers as decoded. If the derivative loses its EXIF orientation tag and renders 90° rotated, both buffers are still compared pre-rotation, so the score stays ~0.99 — a perfect grade on a visibly broken image. Colour-profile loss (P3 → untagged sRGB) is likewise invisible to a luma-only comparison.

This is why orientation and ICC preservation is a generator rule (see the model) rather than something the metric is trusted to catch. The safety net does not cover the most probable failure, and pretending otherwise was the most dangerous thing in r1. fixed in r2

A low score is information, not an error. Nothing is blocked, no derivative is withheld. The flagged list exists so that once, after the first backfill, you can look at three files instead of four hundred and decide whether any of them deserve a per-file exception.

Keeping caches honest

new in r2 decided in r3  R1 missed this entirely, in the one mode the feature exists to serve.

Browsers and CDNs keep a copy of every image, keyed by its web address. The plan regenerates derivatives quietly and in place, under the same filename — so a quality change produces new bytes at an address the cache already thinks it knows. Visitors keep seeing the old image. In bundled-glob mode Vite hashes every asset URL and this never arises; in baseUrl mode — how nicb.at serves — nothing does that for us.

The decision

Phase 1 ships clean filenames with a one-hour cache lifetime. The cost is that a preset change takes up to an hour to reach every visitor, and that repeat visitors re-check images more often than they strictly need to. Both are acceptable for a personal site that changes its compression settings roughly never.

Deferred — revisit if image links ever get shared, or the site feels slow

The concern, as raised: hashed filenames make image URLs unshareable — someone copying a link to an image on the site gets an opaque, expiring address.

Why it was judged acceptable to defer: only derivatives would carry a hash, and derivatives are the small grid thumbnails. The full-size image — the one a visitor clicks into, right-clicks, and shares — is the untouched original at /media/sunset-over-tokyo.jpg, and page URLs never contain an image filename at all. So the ugly address would only ever surface if someone deliberately copied the link of a grid thumbnail, which is both rare and the wrong image to share. Not worth paying for up front.

The one case that would change the answer: og:image. If a social preview ever points at a derivative rather than an original, a versioned URL would 404 for re-scrapes after a sweep. Point og:image at an original and this stays a non-issue.

Preferred shape when it is picked up: version the directory (/derived/web.a1b2c3/sunset.webp) rather than the filename. Same invalidation, but the saved file keeps a clean name — and since a preset change invalidates every file in that preset at once, per-preset is the correct granularity; per-file hashing is over-granular. Rejected alternative: a ?v= query string, because some CDN configurations drop query strings when computing a cache key, which reintroduces the bug invisibly.

Why deferring is cheap: the plan already forbids reconstructing derivative filenames — every lookup reads file_name from the manifest. That single invariant makes the naming scheme a swappable detail, so adopting versioned URLs later is a regenerate-and-sweep (one button on the Compression page), not a migration.

Verify before phase 1 lands

This decision assumes cache headers can actually be set on these assets on Vercel — normally a few lines in vercel.json. If that turns out to be awkward, the deferral is void and versioned URLs move back into phase 1, because clean names with an uncontrolled cache lifetime is the one combination that is genuinely broken: a changed image that never reaches anyone.

Sweeping either way

Regeneration can leave unreferenced files behind (a preset deleted, a source removed, or — later — a superseded version). A sweep deletes anything under derived/<preset>/ the manifest no longer references, run after a backfill and available as a manual action. In classic mode it can run automatically; in static-assets mode it should wait for the next full export, since a deployed site may still reference the old file.

Reader API

Exactly the nicb.at case you described: compressed thumbnails in the grid, the untouched original when someone clicks through.

Resolution order

  1. The named preset for this item, if it was generated.
  2. Nothing else. Fall straight through to item.src.

There is deliberately no "nearest preset" fallback. A component asking for 'thumb' and silently receiving a 4 MB original is a bug you'd never see in development and would only discover in your bandwidth bill; falling back to the original is also that, but it is at least the documented behaviour and it can never render broken. item.variantInfo('thumb') returns null when the preset is absent, so a host that wants to be strict can be.

Host wiring

const mm = MediaManager.load({
  data:    import.meta.glob('$assets/media_manager/**/*.json', { eager: true, import: 'default' }),
  files:   import.meta.glob('$assets/media_manager/media/files/*', { eager: true, query: '?url', import: 'default' }),
  derived: import.meta.glob('$assets/media_manager/media/derived/*/*', { eager: true, query: '?url', import: 'default' })
});

The preset name comes from the glob key's directory segment, so no extra config is needed and adding a preset needs no host change. In baseUrl mode the reader synthesises ${baseUrl}/derived/${preset}/${file_name} from the manifest, matching how src is already synthesised today. The derived map is optional — a host that omits it gets originals everywhere, which is exactly the pre-compression behaviour, so this is a non-breaking reader change (WorkspaceGlobs.posts is the existing precedent for an optional third map).

The derived map must be its own index — sharing one would break originals

assetIndex is a single flat map keyed on lowercased bare basename, and baseUrl synthesis fires only when assetIndex.size === 0 (reader/media-manager.ts:144-153). Folding derivatives into that map has two independent failure modes: it makes the index non-empty, which silently disables baseUrl synthesis for the originals — every item.src goes null and every file reports missing: true — and bare-basename keying would collide derived/web/x.webp with derived/thumb/x.webp.

So the derived index is a separate, preset-keyed map, not a reuse of the existing one. R1's directory-segment rule was right about the collision but silent about the size === 0 gate, which is the more dangerous of the two. fixed in r2

Scope note: "cleanly addable" is accurate but not free — MediaItem has an all-readonly fixed constructor and is built at two sites, and WorkspaceGlobs / ParsedWorkspace / ReaderContext each need the new optional map. Roughly six touchpoints across three files.

Phases

Phase 1
The twin

One derivative per image, measured and reported

Adopt sharp. Preset registry in media/settings.json with a workspace default only — no per-class subscription, no widths, so there is no union to resolve yet. Auto-on-upload, backfill job, quiet stale regeneration, SSIM scoring, the Compression page, and item.variant() in the reader.

Done when

  • ManifestEntrySchema and the reader's parseManifest both declare derived, and a membership write followed by a re-read preserves it (the zod-strip regression test).
  • reconcile() records/refreshes size for adopted and re-uploaded blobs — file:size stops rendering empty for hand-dropped files.
  • media/derived/<preset>/ is populated for every compressible blob; originals byte-identical.
  • Two originals sharing a stem (photo.jpg + photo.png) produce two distinct derivative filenames, both resolvable.
  • Derivatives are served with an explicit, verified cache lifetime — confirmed reachable on Vercel before this phase is considered done.
  • A sweep removes derivatives the manifest no longer references, and never removes one it does.
  • A derivative of a rotated phone photo renders the same way up as its original, and retains its ICC profile.
  • Entries carry size, ssim, recipe, source_size; skipped entries carry skipped and recipe, and are not retried on a second backfill.
  • Uploading a JPEG produces its derivative without delaying the upload response. So does a Google Photos import.
  • Changing the quality setting marks derivatives stale and regenerates them without a prompt.
  • Renaming a blob renames its derivatives; deleting a blob deletes them; deleting media/derived/ and running a backfill reproduces byte-identical derivatives with equal size/ssim/recipe (not "the exact same state" — generated_at necessarily differs).
  • Switching storage location moves derivatives too, and the free-space preflight counts their bytes.
  • A backfill of 400+ files does not cause request failures from manifest-lock contention.
  • /compression shows saved bytes, coverage, the SSIM histogram, per-class breakdown, and the flagged list.
  • A host passing a derived glob gets compressed URLs from item.variant(); a host that doesn't is unaffected, including in baseUrl mode.
Phase 2
The ladder

Widths, class subscriptions, srcset

Add width to the preset shape and per-class subscription to EntitySettingsDialog — the union rule goes live here. Add item.srcset(), the per-file Compression section, and the file:saved / file:quality verbose fields plus their sort keys.

Done when

  • A blob in two classes with different subscriptions has one derivative per distinct preset, and removing it from one class doesn't delete a derivative the other still wants.
  • A width-bearing preset produces correctly-sized output with aspect ratio preserved and its SSIM computed against a matched-size original.
  • item.srcset() emits every width-bearing preset with correct w descriptors, and variantInfo() returns the derivative's dimensions, not the original's.
  • file:saved, file:quality and file:presets appear in the Show menu and are usable as sort keys.
  • Deleting a preset removes its directory and its manifest entries, and nothing else.
Phase 3
Motion

Video, if it ever earns its place

Not scheduled. Recorded here only so the phase-1 data model doesn't assume image-only: recipe is an opaque string and derived is a preset-keyed map, both of which describe an ffmpeg output as happily as a sharp one. The real cost of this phase is the dependency and the encode queue, not the schema — which is the point of writing it down now and building none of it.

Risks & calls made for you

Stem-mirrored filenames — two holes, both closed

Collision. photo.jpg and photo.png both want photo.webp. On generation, if the target stem is already taken within that preset directory by a different file id, append a short id suffix (photo-8f3a1c.webp). The resulting name is stored in the manifest, so lookup is always a manifest read and never a reconstructed string. back in r3 — r2 deleted this rule on the grounds that content hashing made collisions impossible; with hashing deferred, the rule is needed again.

Rename still needs a hook. renameBlobById (classRepo.ts:1245) is genuinely O(1) — disk rename plus one manifestRenameFileId — and adding one rename per preset keeps it a small constant. Verified. Note its rollback path (classRepo.ts:1261) gains more partial-failure states, so the derivative renames should happen after the original's rename succeeds, and a failure there should be logged rather than rolled back: a stale derivative filename is harmless (the manifest still points at it), a half-rolled-back rename is not.

Concurrency is tighter than r1 implied — real numbers

R1 said "a worker queue bounded at cpus − 1" and "don't hold the lock across an encode". Both correct, and the lock-ordering rule it cited is real (manifest.ts:22-25). But it understated the constraint:

  • withFileLock retries 40 times with 10 + attempt×5 ms backoff — ~4.3 s then it throws (lock.ts:19-49). Every grid read goes through listAllFiles → reconcile, which takes the same lock. A backfill doing one lock-acquire per file will start failing user requests.
  • Each result-write is an O(n) rewrite of the whole manifest JSON. 412 files ⇒ 412 full rewrites.
  • The 10 s stale-lock TTL (lock.ts:37-42) means a holder that overruns gets its lock deleted by a waiter → two concurrent writers → lost derived blocks.

So: batch manifest writes (one write per N completed results, not per file), and bound worker concurrency against lock contention, not just CPU count. This is the one piece of real infrastructure in phase 1, and it is larger than r1 made it sound. fixed in r2
