media-manager · plan

Static assets: a separate blob store, with auto-detect & export

Let a media-manager workspace keep its binary files outside the workspace — in the host site's static folder — so they're served straight from a CDN and never bundled into a size-limited serverless function. Configurable per project, auto-detected where possible, and reversible via an export that reunites everything into one self-contained folder.

0 The problem, in plain terms

A media-manager workspace stores its photos inside itself, at <root>/media/files/. A host site (nicb.at) bundles that workspace with Vite so the reader can resolve photo URLs. The current reader recipe uses an eagerly-evaluated ?url glob over media/files/* — which runs in server-reachable module scope, so Vite's SSR build emits every photo as a bundled asset and adapter-vercel copies them into the serverless function.

Result: 236 MB of photos land inside a 250 MB-capped function and the deploy fails — even though the very same bytes also sit in the CDN static output (uncapped) where visitors actually read them. The bundled copy is pure dead weight.

The core fix is settled & verified: feed the reader plain URLs (/media/<file>) and stop bundling the binaries. The reader only ever does a case-insensitive filename → string lookup (media-manager.ts:210), and dimensions come off the manifest, not the bundler (manifest.ts:88) — so nothing about item shapes changes. This plan is the configurable, reusable version of that fix, built into media-manager itself instead of hand-rolled per site.

1 Decisions locked with you

Blob location
Photos live on their own in the site's static folder (e.g. static/media/) — the binaries' only home. No copy step; no duplicate tree.
Configurable
Where that folder is (and the web address it's served at) is configured per project in media-manager.config.json, with a sensible default per framework.
Auto-detect
media-manager tries to detect the static folder from the host repo (SvelteKit static/, Next/Astro public/…) and proposes it for you to confirm.
Reader
A baseUrl option on the reader synthesizes URLs from the manifest — no ?url glob. (Already agreed.)
Fallback
The editor sometimes runs standalone. When no static folder is configured, it falls back to the classic in-workspace media/files/ store. Static mode is strictly opt-in; existing workspaces are untouched.
Export
export produces a re-openable, self-contained workspace — binaries reunited with their info in one tidy tree. Doubles as backup / move-to-another-site.
Sequencing
Build the whole feature first, then switch nicb.at over in one go. The deploy stays as-is until the cutover (§9).

2 Two modes & the one seam that switches them

Everything hangs off a single decision: where is the blob directory? Today that's hardcoded to <root>/media/files via getGlobalFilesDir() (src/lib/storage/paths.ts:58). Make that function config-aware and both modes fall out of it — because every consumer (upload, blob serving, EXIF, rename, delete, manifest reconcile, missing-file scan) already routes through it.

DEFAULT  Classic / in-workspace

No assets config resolved.

# binaries live inside the workspace
<root>/media/files/olympic_river.jpeg
# reader still uses the ?url glob (bundled, hashed)

Standalone edits, existing sites, the committed test-fixture — all keep working with zero change.

OPT-IN  Static / separate blob store

assets.dir points at a served folder.

# binaries live in the site's static dir
<site>/static/media/olympic_river.jpeg
# workspace holds only JSON; reader uses baseUrl
<root>/media/  (manifest.json, classes/, no files/)

Served from the CDN at /media/…; never bundled into the function.

How the mode is chosen (per invocation): if an assets.dir is configured and exists on disk → static mode; otherwise → classic. The resolved absolute dir + base URL are handed to the server via env (mirroring how the root already flows into paths.ts).
Precedence gotcha (must fix in P1): assets lives only in media-manager.config.json, but resolveRoot() (bin/media-manager.js:151) short-circuits and never reads the config file when the root came from a CLI arg or MEDIA_MANAGER_ROOT env. So the config-only assets block would be silently skipped in exactly those modes. Fix: always locate + read the config file for the assets block regardless of how root was resolved (the nicb.at cutover is config-driven, so it's unaffected — but the plumbing must not depend on that).

3 The config shape

One additive block in the existing media-manager.config.json (already discovered by walking up from cwd — bin/media-manager.js:36,131). Paths are resolved relative to the config file, exactly like root is today.

{
  "root": "./src/assets/media_manager",
  "assets": {
    "dir":     "./static/media",   // where blobs live & are served from
    "baseUrl": "/media"            // web-address prefix the reader uses
  }
}
  • Both fields optional. Absent assets ⇒ classic mode. This is the whole backward-compatibility story.
  • dir is namespaced (a dedicated media subfolder, not the bare static/) so the manifest's disk-reconcile never adopts unrelated files the site keeps in static/.
  • baseUrl is what the reader prefixes onto each filename. (Stretch: let the reader read this from the workspace settings.json so the host needn't pass it at all — noted in §6, not required for v1.)

4 Build plan (feature-first, then cut over)

P1

Config resolution & the paths seam

Foundation. No behavior change yet — just the plumbing that lets the blob dir move.

  • Extend config load (bin/media-manager.js) to parse the optional assets{ dir, baseUrl }, resolve dir to an absolute path relative to the config file, and export both to the server via MEDIA_MANAGER_ASSETS_DIR / MEDIA_MANAGER_ASSETS_BASE_URL env.
  • Fix the precedence short-circuit (resolveRoot, bin/media-manager.js:151): it returns before reading the config file when root comes from arg/env, so the config-only assets block gets skipped. Always locate the config for assets, independent of how root resolved. Validate the dir is sane (don't silently point the blob subsystem at an arbitrary path).
  • Make getGlobalFilesDir() (src/lib/storage/paths.ts:58) return the configured assets dir when set, else <root>/media/files. Add getAssetsBaseUrl().
  • Audit for hardcoded media/files — everything must go through the accessor. Known consumers: upload (/api/files/upload), blob serve (/api/files/[id]/blob), EXIF (server/fileMetadata.ts), rename/delete (classRepo.ts · renameBlobById/deleteFromDiskById), manifest reconcile (manifest.ts), missing-refs (listMissingFileReferences).
P2

Editor stores & serves blobs from the static dir

  • With P1 in place this is mostly verification: uploads land in the static dir, thumbnails serve from it, rename/delete/EXIF operate on it, and manifest reconcile scans it (adopting new blobs, flagging vanished ones).
  • Make reconcile safe for a shared/misconfigured dir (the sharpest risk). reconcile (manifest.ts:283) currently auto-adopts every disk basename not already in the manifest, on every list call — its only filter (readGlobalBlobNames / NON_BLOB_NAMES, manifest.ts:11,316) excludes dotfiles + a few known JSON names, not arbitrary images. So pointing dir at a shared static/ would silently pull favicon.png, og-image.jpg, … into the manifest. Enforce, don't just recommend, the dedicated subfolder: init/ config/export create and exclusively target a media subdir, and gate manifest adoption in static mode so a stray file can't enter the manifest on first serve.
  • Note the mkdirSync(filesDir) on the upload paths (/api/files/upload/+server.ts:30 · google-photos import): in static mode a mistyped dir silently materializes a stray directory. Prefer doctor-validated existence over auto-creating outside <root>.
  • Unit tests over a temp root with an assets.dir pointed elsewhere; assert the manifest + on-disk placement + blob serving all follow the seam, and that a non-blob file in the dir is not adopted.
P3

Auto-detect + config / init / doctor UX

  • Detector over the config-file directory (the host repo root): SvelteKit (svelte.config.* + static/) → ./static/media + /media; Next/Astro (next.config.*/astro.config.* + public/) → ./public/media + /media; generic public/ fallback; else leave unset (classic).
  • Propose-and-confirm in init/config: print the guess, let the user accept or override, then write the assets block.
  • doctor reports the resolved mode + assets dir/baseUrl and fails loudly (not just warns) on: dir missing, dir not the dedicated subfolder, dir empty while manifest lists blobs, filename present on disk but absent from manifest (and vice-versa), and case-collisions (§8). This is the recovered build-time existence check.

5 Reader baseUrl mode — the surface

Purely additive to the pure reader. The host stops passing a files glob and passes a base URL instead:

const mm = MediaManager.load(
  {
    data: import.meta.glob('$assets/media_manager/**/*.json', { eager: true, import: 'default' }),
    // no files glob — binaries aren't bundled anymore
  },
  { assets: { baseUrl: '/media' } }
);

Inside the reader constructor (media-manager.ts:126), after the manifest is parsed: if the asset index is empty and options.assets.baseUrl is set, fill it straight from the manifest —

for (const entry of Object.values(this.manifest.files)) {
  assetIndex.set(entry.file_name.toLowerCase(),
                 joinUrl(baseUrl, encodeURIComponent(entry.file_name)));
}
ConcernHandling
Both modes at oncebaseUrl only kicks in when no ?url glob populated the index — so hosts under the size limit keep hashed, content-addressed assets unchanged.
URL encodingencodeURIComponent per filename (spaces / # / ?). One implementation, in the library.
missing semanticsDegrades from a build-time existence check to whatever the manifest claims; a truly absent binary becomes a runtime 404. doctor + export-time verify (§8) recover the build-time signal.
Case collisionsIndex is keyed on lowercased basename. Assert no two file_names collide when lowercased (the manifest is flat & currently collision-free).
Cache-bustingDeferred. Names are camera-unique/immutable, so exposure is narrow. A later ?v=<hash> needs a per-blob hash in the manifest — separable, reader needs no change (still a string).

6 The export command

npx media-manager export <dest>   # reunite into a self-contained workspace

Writes a canonical, classic-layout workspace to <dest>:

  1. Copy the JSON tree verbatim — settings.json, media/manifest.json, media/classes/, records/, globals/.
  2. Copy every blob from the configured assets dir into <dest>/media/files/ (reuniting bytes with their info).
  3. Verify each manifest.file_name resolved; report any missing / colliding.
The result opens with npx media-manager <dest> in classic mode and needs no static folder around it — so it's a proper backup, a hand-off, and the portability answer for moving a static-mode workspace to a new machine or site.

7 Risks & known limitations

ItemNote / mitigation
commit Blobs must be committed In this model the static dir is the blobs' only home — so static/media/ is committed to git (unlike a copy/sync approach, which would gitignore it). No duplication in the working tree; the workspace's media/files/ simply doesn't exist in static mode.
standalone Editing without the static folder Opening a static-mode workspace without its static dir (e.g. you copied only the JSON) shows blobs as missing — they live in the site repo you didn't bring. This is inherent to splitting. export is the fix: run it first to get a self-contained tree. The chosen fallback only governs new standalone workspaces (no config ⇒ classic media/files).
shared dir Static folder holds other files Sharpest risk. Reconcile auto-adopts every unknown basename in the blob dir (manifest.ts:283), so a shared static/ would pull the site's favicon/OG images into the manifest on first serve. Mitigation must be enforced, not advisory: init/config create & exclusively target a dedicated media subfolder, and adoption is gated in static mode (see P2). doctor fails on a non-dedicated dir.
missing Build-time existence check lost Covered above (§5). Restore the signal via doctor + export-time verification.
env-only Single-node assumption unchanged The assets dir flows via env like the root does; the coarse .lock mutex still assumes single-node. No change to that contract.

8 nicb.at cutover (§P7, after the feature lands)

  1. Add the assets block to nicb.at's media-manager.config.json (auto-detected: ./static/media + /media).
  2. Move existing binaries src/assets/media_manager/media/files/ → static/media/ (a one-time git mv; they stay committed).
  3. In the reader call, remove the files ?url glob and add { assets: { baseUrl: '/media' } }.
  4. Run npx media-manager doctor first — the intended pre-cutover gate. It hard-fails on a manifest blob absent from the static dir (a runtime 404) or a case-insensitive filename collision (which would throw the whole reader build in baseUrl mode), and warns on stray non-blob files.
  5. Keep the OAuth secret out of the bundle: if src/assets/media_manager/media/google.json exists, exclude it from the data glob (import.meta.glob(['…/**/*.json', '!**/google.json'])) or don't commit it — the **/*.json glob would otherwise bundle it into the build.
  6. Verify: 
    npm run build
du -sh '.vercel/output/functions/…/catchall.func'   # ~5M, was 241M
du -sh '.vercel/output/static/media'                # the bytes, CDN-served
grep -rn "query: *'?url'" src/                       # no hits under media/files
npm run check && npm run test:e2e                       # /photos still renders
The e2e run matters most: a broken asset map degrades to a silently empty gallery (fetchImageList filters on truthy src), so it would render blank rather than fail loudly. Keep that test in the gate.

Scope note (unchanged from the source spec): this removes the 250 MB constraint permanently but does not make the site fast — originals are full-res camera files (~3.8 MB avg). Resizing/re-encoding is a separate, still-worthwhile pass that could also live in a media-manager export step later.
